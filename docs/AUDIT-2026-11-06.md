# mooi — full audit, third pass

Date: 2026-11-06 · HEAD `5018704` (`main`, 12 files modified in the working tree) · Pleamar
0.7.11 (language 0.9) · Lua 5.4 · no live session was started.
Scope: `bin/mooi`, every scene and logic file, `shell/lib`, `shell/ui`, `shell/theme`,
`shell/player`, `shell/bmo`, `tools/`, `tests/`, the setup snapshot, the GitHub workflow, and the
documents that describe all of it. Predecessors: [AUDIT-2026-10-31.md](AUDIT-2026-10-31.md) and
[AUDIT-2026-11-01.md](AUDIT-2026-11-01.md); their still-open items are re-checked here.

## Method

1. `bin/mooi check` on the working tree: **12 scenes compile, 389 unit tests, 0 failed, 27 BMO
   tests, 0 failed, exit 0** (Pleamar 0.7.11 · language 0.9).
2. Static reading of the launcher, the settings/theme paths, the weather and network paths, the
   scene monoliths, and every write site for `settings.json`.
3. Generator determinism: `shell/` and `tools/` were copied to `/tmp`, `tools/gen-settings.py` and
   `tools/gen-frame.py` were run there, and the result compared with the tree — **no diff**.
4. Documentation cross-check: every suite named in `docs/TESTING.md`, every version claim, every
   program in `docs/ARCHITECTURE.md`, and every open item in `docs/TODO.md` against the tree.
5. Repository checks: `git ls-files`, `git check-ignore`, `git diff --numstat`, and a probe file to
   test whether a new contribution is visible to `git`.

Not done: no scene was started, no pointer or key was sent, `shellcheck` is not installed on this
machine, and no GitHub Actions run was queried. The limitations are repeated at the end.

## Verdict

The engineering core is still strong: the gate passes, the pure logic is well factored, the
settings write policy exists and is used by the bar, the settings window and the theme CLI, safe
mode is honoured, commands are argv-only, and each scene has a narrow permission allowlist. The
generators are deterministic, which means generated-output drift can be enforced cheaply.

What this pass found is mostly **around** the code rather than in it: one privacy leak in the
public snapshot, a `.gitignore` that makes every new file invisible to git, a gate that does not
compile the lock screen while claiming to compile every scene, and a documentation layer that has
fallen several decisions behind HEAD. Two engineering items also remain open from earlier audits:
`settings.json` still has a second writing policy, and the Notch/Nexus panels are still duplicated.

### G1 · High · The public snapshot still tracks identity images — privacy

`git ls-files` at HEAD lists:

```
setup/home/.local/share/pleamar/mooi/identity/avatar-1793267813-79252.jpg   (2.1 MB)
setup/home/.local/share/pleamar/mooi/identity/banner-1793808602-2418781.png (1.7 MB)
```

`README.md:5` and `setup/README.md` say identity assets are excluded, and
`setup/capture.sh` does not copy `identity/` (it writes only neutral `settings.json`,
`notes.json`, `board.json` and `stash.json`). The files are therefore stale from before the
sanitisation commit and remain in the tree and in history. `.gitignore`'s `identity/` rule cannot
untrack a file that is already tracked.

The rest of the snapshot is genuinely neutral: `notes.json` is `{"notes":[]}`, `board.json` has
three empty columns, `settings.json` is `{"version":2}`, and `capture.sh` runs a credential scan
before replacing the snapshot. The two images are the exception.

**Fix:** confirm whether these are the author's own pictures. If yes, `git rm` them from
`setup/home/.../identity/`, and rewrite history (e.g. `git filter-repo --path-glob
'setup/home/.local/share/pleamar/mooi/identity/*' --invert-paths`) with an explicit force-push
decision; a normal deletion only removes them from HEAD. If they are stock images, say so in
`setup/README.md` and keep them intentionally. Add a pre-commit or CI assertion that
`setup/home/**/identity/` is empty.

### G2 · High · `.gitignore` ignores every new file

```gitignore
!important
!
**
!setup/home/**
```

Line 6 ignores everything; line 9 un-ignores only `setup/home/**`. Verified:

```text
$ printf 'test\n' > probe-new-file.md
$ git check-ignore -v probe-new-file.md
.gitignore:6:**    probe-new-file.md
$ git status --porcelain probe-new-file.md
(no output)
```

Consequences for a public repo:

- A contributor's new test, doc, scene fragment or packaged theme is invisible to `git status` and
  must be added with `git add -f`. Most people will not know that; the work silently disappears.
- The global `*.png` / `*.jpg` rules (lines 28–29) also block new setup assets and docs images;
  the existing tracked images only survive because they predate the rule.
- `setup/README.md`'s `git add -A setup` works only because of the `setup/home/**` exception.
- This audit document is itself ignored until added with `-f`, which demonstrates the problem.

**Fix:** stop ignoring `**` and enumerate the runtime files (lines 12–32 already do that). For the
setup baseline, keep `!setup/home/**` only if a deny-by-default tree is really wanted, and add
`!setup/home/**/*.png` / `*.jpg` so new baseline assets can be added. After changing it, run
`git status --porcelain --ignored=no` once and stage only what belongs in the repo — local agent
state and caches will appear for the first time.

### G3 · High · `bin/mooi check` does not compile the lock screen, though every document says it does

`bin/mooi:1604–1615` compiles twelve scenes with twelve explicit `--check` calls:

```
mooi.plm, mooi-settings.plm, mooi-board.plm, mooi-nexus.plm, mooi-frame.plm, mooi-desk.plm,
mooi-player.plm, mooi-notch.plm, mooi-widgets.plm, mooi-walls.plm, mooi-viz.plm, bmo/bmo.plm
```

`shell/mooi-lock.plm` exists, is listed in the launcher's own `SCENES` list (`bin/mooi:958–970`,
`mooi-lock.plm:the lock screen`) and is compiled by `snapshot()` through that list
(`bin/mooi:985`), but the documented gate does not compile it. `docs/TESTING.md:7` says `check`
“compiles every scene”. A lock-screen syntax or permission error therefore passes `bin/mooi check`
and only surfaces when the session next locks — the worst moment to discover it.

**Fix:** make the gate enumerate, not list:

```sh
for scene in "$root"/shell/*.plm "$root"/shell/bmo/*.plm; do
    "$pleamar" --check "$scene" || exit 1
done
```

Add a unit or check assertion that the set of `shell/**/*.plm` files equals the set compiled, so a
new scene cannot be forgotten again.

### G5 · Medium · `settings.json` still has two writing policies, and three writes fail silently

`shell/lib/settingsfile.luau` is the right policy: read the file as it is now, lay only the leaves
this program changed over it, write. The bar (`shell/mooi.luau:331`), the settings window
(`shell/mooi-settings.luau:414`) and the theme CLI (`shell/theme-cli.luau:328`) use it.

The player does not. It re-reads and then writes the **whole** document:

- `shell/mooi-player.luau:426` (library group/sort)
- `:505` (visualiser style)
- `:520` (player view)
- `:546` (cover/shell tint)

Three of the four wrap the write in `pcall` and discard the result; a read-only data directory, a
full disk or a permission error leaves the UI changed with no message. Only `:546` reports
`COULD NOT SAVE THE SETTING`. Re-reading narrows the race but does not remove it: a change made by
the bar between the read and the write is still reverted, and a whole-document write can resurrect
a key another program removed.

**Fix:** route all four through `settingsfile.save(sys, "settings.json", before, after, read)`, and
make a failed save visible (`say("COULD NOT SAVE THE SETTING")`) and logged. Add a small source
check (or a unit test over a table of write sites) that no logic file calls
`files.write("settings.json", …)` outside `lib/settingsfile`.

### G6 · Medium · CI is green but not hardened, and it duplicates the local gate

`.github/workflows/check.yml`:

- has no `permissions:` block, so the job runs with the default `GITHUB_TOKEN` permissions instead
  of `contents: read`;
- has no `concurrency`, so a push to a PR branch starts both a `push` and a `pull_request` run;
- has no `timeout-minutes`;
- pins `actions/checkout@v4` by tag, not by commit;
- re-implements the gate as separate steps instead of calling one script, so it has already drifted
  from `bin/mooi check`: CI runs `tests/components.sh` and shellchecks `setup/*.sh`, while the local
  gate runs neither;
- does not check that generated scenes match their generators, although both generators are
  deterministic today (verified) and `shell/mooi-settings.plm` + `shell/mooi-frame.plm` are
  committed build products.

**Fix (small, all in one file):**

```yaml
permissions:
  contents: read
concurrency:
  group: check-${{ github.ref }}
  cancel-in-progress: true
on:
  push:
    branches: [main]
  pull_request:
```

then add one step after the unit suites:

```sh
python3 tools/gen-settings.py
python3 tools/gen-frame.py
git diff --exit-code -- shell tools
```

and call `sh tests/components.sh` from `bin/mooi check` too, so “local gate” and “CI gate” mean the
same thing.

### G7 · Medium · Four independent IP-geolocation lookups, three weather fetchers

`https://ipinfo.io/json` is called from four places:

- the bar's weather module (`shell/bar.luau:269`)
- the weather island (`shell/islands.luau:145`)
- the notch (`shell/mooi-notch.luau:925`)
- the Nexus (`shell/mooi-nexus.luau:741`)

The notch and the Nexus share `nexus-weather.json` and the `lib/weathercache` validator (good), but
each still performs its own IP lookup on a cold cache; the bar fetches its own forecast and does not
use that cache at all. With a weather panel open, the public IP can be disclosed three times in one
session, and the bar behaves differently from the panel that shares the same screen. This is the
same issue as F9 (2026-10-31), now with a fourth site.

**Fix:** extend `lib/weathercache` with a location memo
(`~/.cache/mooi/ipinfo.json`, bounded latitude/longitude, a 24 h TTL) and have all four call it;
then have the bar read the shared forecast cache instead of fetching its own. One egress path, one
place to document the privacy behaviour, one place to disable it.

### G8 · Medium · The Notch and the Nexus still implement the same panels twice

F10 (2026-10-31) is still open. The two logic files share twelve same-named local helpers —
`launch`, `read`, `read_text`, `paint`, `place`, `trim`, `decode`, `env`, `show_weather`, `take_viz`,
`rest_viz` — and both write `nexus-weather.json`. This duplication is where the dead
`nt_studio` handler came from, and it is the main reason a change to the weather, Claude, GitHub or
media presentation has to be made twice.

**Fix:** keep the incremental plan from F10 — move the shared panels into `shell/ui/` includes and
the pure decisions into `shell/lib/`, one panel per change, with `bin/mooi check` after each. Start
with weather: it is already shared through `lib/weathercache`, so it has the smallest behavioural
surface.

### G9 · Medium · Committed generated scenes have no provenance marker or drift gate

The largest files in the repo are generated or generated-adjacent:

| File | Lines | Size |
| --- | --- | --- |
| `shell/mooi.plm` | 5,893 | 429 KB |
| `shell/mooi-settings.plm` | 4,789 | 353 KB |
| `shell/mooi-frame.plm` | 3,688 | 310 KB |

`tools/gen-settings.py` rewrites the settings window and edit-mode grips; `tools/gen-frame.py`
rewrites the frame. Neither output carries a “generated, do not edit” header (a search for
`generated`/`do not edit` in the `.plm` files finds none), and no gate re-runs them. Today the
outputs are in sync, but the working tree already contains a 154/59-line change in
`mooi-settings.plm` and a 0/228-line change in `mooi-frame.plm` next to the generator changes — the
exact shape that leads to a hand edit being overwritten on the next run.

**Fix:** emit a three-line header from both generators
(`// generated by tools/gen-*.py — edit the spec, not this file`), and add the CI drift step from
G6. Keep generator and generated output in the same commit.

### G10 · Medium · The working tree mixes an unfinished feature, generated output and docs

`git diff --numstat` shows twelve modified files, +431/−305, spanning:

- the launcher (+150), config schema (+20), setters (+5), settings index (+12/−8),
  settings logic (+34/−1), generated settings scene (+154/−59), generated frame scene (0/−228);
- `tools/gen-settings.py` (+30/−1) and `tools/gen-frame.py` (+8/−6);
- the workflow (+4) and two documents (`TESTING.md` +2, `THEME-PACKAGES.md` +12/−2).

No single commit can describe this, and a reader cannot tell which parts are the intended change
and which are regenerated consequences. The frame scene losing 228 lines is especially hard to
review without the generator diff beside it.

**Fix:** commit in three units — (1) generator + generated output, (2) settings schema/logic/index
feature, (3) docs/workflow — and run `bin/mooi check` before each. Do not leave a generated scene
modified without its generator in the same commit.

### G11 · Low · The unit suite is one 4,292-line file, and `settings_index` has no tests

`tests/unit/run.lua` is 4,292 lines with 389 `test(…)` calls in one process. It has section prints
(`config`, `wfx`, `hypr`, … `wallpapers`) but no filtering, so a contributor must run everything to
check one module, and one leaked global can affect later tests. Every `shell/lib` module is
exercised except `settings_index`, which drives the settings window's search and reset-by-page
(`shell/mooi-settings.luau:13`, `:483`, `:531`).

**Fix:** split the file into `tests/unit/suites/*.lua`, required by a small runner with
`--filter <section>`, and add tests for `settings_index` (row count, page/section grouping, search
matching, and that every setter code in the schema has exactly one row).

### G12 · Low · Local gate, CI and the test table do not agree

- `bin/mooi check` does not run `tests/components.sh`; CI does.
- CI shellchecks `setup/*.sh`; `bin/mooi check` only shellchecks itself and `tests/*.sh`.
- `docs/TESTING.md` has no row for `components.sh` and still describes `wallpaper.sh`.
- CI cannot run `tests/surfaces.sh` (it needs Pleamar), which is documented, but nothing marks that
  suite as “local only” in the table.

**Fix:** one `tests/gate.sh` invoked by both `bin/mooi check` and CI, with an explicit
`--no-pleamar` mode for the runner; generate the table's command column from the scripts' own usage
strings.

### G13 · Low · Old audit F12 items are still in the tree

- `bin/mooi:1529` rejects only `\001` and `\177` in an identity name; every other C0 control still
  reaches a name that is drawn on the Nexus plate. Reject `[[:cntrl:]]` (or the Lua equivalent at
  the write boundary).
- `settings_link` (`bin/mooi:919`) still moves a real data folder to `*.old.$$` and never cleans
  up; repeated renames accumulate.
- The wallhaven key path is documented as `~/.config/mooi/wallhaven.key`
  (`shell/lib/config.luau:461`) while the settings window writes `wallhaven.key` into mooi's data
  folder (`shell/mooi-settings.luau:742`) and the launcher checks the data folder first
  (`bin/mooi:735–736`). The settings code comments that `files.write` gives the file mode 0600, but
  nothing in this repo verifies that, and `mooi wall whkey` refuses anything not exactly 600. Pick
  one canonical path and test the mode after a save (there was no key on this machine to inspect).
- `theme_sync` still substitutes the repo path into TOML with `sed "s|@TPL@|…|"`; a repo path
  containing `&` or `|` mangles the result. Escape the substitution or render the file with `awk`.

### G14 · Low · `STATUS.md` no longer works as a status entry point

`STATUS.md` is 140 KB in 352 lines, newest-first, with single paragraphs of 2,305–2,711
characters. Its first entry is 2026-11-04/D157, while HEAD already contains D160–D162. A reader

**Fix:** move the dated entries to `docs/CHANGELOG.md` (or generate them from `DECISIONS.md`), and
keep `STATUS.md` to one screen: what is built, what is verified and when, the five open items, and

### G15 · Low · No licence and no security policy

The repository is public and handles an API key, network requests and a lock screen, but has no
`LICENSE` and no `SECURITY.md`. Without a licence the default is “all rights reserved”, whatever the

**Fix:** add the licence the author intends (check Pleamar's licence for compatibility) and a short

## Improvement opportunities by area

These are not defects; they are the places where the next increment would buy the most.

**Product / UX**

- Theme packages are a pure model with a terminal interface; a browser and a visual editor are the
  documented next step (`docs/THEME-PACKAGES.md`). A “preview before apply” and a revert to the
  previous package would make sharing safe.
- Multi-monitor is repeatedly listed as unverified. A second-monitor pass over the bar, notch,
  Overview, deck and lock screen is worth more than any new surface.
- Onboarding on a fresh machine is a clone plus `setup/install.sh`, then log in again. A
  `mooi doctor` that checks the optional tools, Pleamar version/language, Hyprland IPC, a writable
  data folder and the lock/idle wiring would turn the README's “Needs …” line into a diagnosis.
- The launcher has ~45 verbs; `mooi help` prints the header comment, which is good. Generating the
  README's command block from that same header would stop the two from drifting (G4).

**Accessibility**

- Reduced motion, contrast-checked palettes and a battery-aware visualiser already exist — better
  than most shells. The gaps are unverified scale factors (25 % / 150 %), focus visibility on every
  control, and text size as a first-class setting rather than a corner-size scale.
- The lock screen and the settings window are the two surfaces a keyboard-only user meets first;
  they deserve the same focus-ring and Escape-contract tests the bar has.

**Performance**

- The newest sample is 374 MB PSS and ~2.2 % of a core idle, with the bar alone at ~306 MB. That is
  the largest single cost in the project. Add a `tools/measure.sh` that records PSS, CPU ticks and
  the scene's own frame report for idle / music / overview / notch open / Nexus open, and keep the
  numbers beside the commit that changes them.
- A written budget (for example: bar under 200 MB PSS, idle under 1 % of a core, p99 under 25 ms)
  would turn “performance work” into a pass/fail check.
- The wallpaper index and thumbnails are cached under `~/.cache/mooi`; an eviction policy and a
  size report in `mooi status` would keep a large picture library from growing without bound.

**Reliability**

- The keeper restarts a scene after a crash and gives up after three quick deaths; make the crash
  count and the last error visible in `mooi status` (and rotate the log) so a repeated failure is
  diagnosable without reading `journalctl`.
- `mooi diagnostics` exists and is local-only; adding the running scene versions, Pleamar
  version/language, and the snapshot stamp would make bug reports self-contained.

**Security / privacy**

- One documented egress list (weather/IP lookup, Wallhaven, GitHub, Claude) with a switch per
  feature would match the project's already-careful tone. Today the behaviour is correct but
  scattered across four files.
- Secret handling is one file (`wallhaven.key`) with a mode check; a small test that writes a key
  in a sandbox and asserts mode 600 would close the one unverified claim (G13).

**Architecture / code**
